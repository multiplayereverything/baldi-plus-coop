# Multiplayer vending synchronization — 0.5.2

Original-code basis: `SodaMachine.ItemFits` accepts its configured required item only while `usesLeft > 0`. `ITM_Quarter.Use` raycasts using the player's reach and click layers; the inventory removes the quarter before `PostUse` calls `InsertItem`. `InsertItem` awards either its configured item or a weighted random selection, decrements stock, and replaces material slot 1 when empty.

The multiplayer quarter path preserves these rules. The host owns each machine's stock and makes weighted selections once. Only the purchasing player's inventory receives the item and loses its quarter. The recipient uses the game's `RemoveItem` and `AddItem`, preserving inventory HUD and item effects. Host-local purchases call the original `InsertItem` directly. Coin doors and other item acceptors retain their original path.

The world snapshot carries machine stock, including empty machines; empty-stock materials update on every client. A purchase reserves stock before sending a grant. Receipts prevent duplicate grants from awarding twice; per-peer request numbers reject replayed requests. Epoch, ready state, elimination, locker state, machine identity, activity, stock and proximity are checked on the host. An explicit failed delivery restores the stock and original material; a disconnected/unknown delivery remains consumed to avoid duplicating stock.

Limitations: this path covers the game's quarter-operated `SodaMachine` variants, including fixed and weighted rewards. Other `IItemAcceptor` implementations are separate gameplay features. The host cannot independently inspect a remote inventory; the client verifies and consumes its reserved quarter slot on receipt. A disconnected purchase may consume stock without an item reaching its buyer. Host migration restarts the floor rather than preserving partially consumed vending stock. Stock synchronization does not create additional dispensing animations or sounds absent from original `SodaMachine.InsertItem`.

Focused lab flag: `-bt-lab -bt-diagnostics -bt-vending-tour`. `artifacts/tests/vending-results.json` reports native valid-item/invalid-item/empty-stock checks, stock restoration, snapshot serialization, request replay/epoch/locker/elimination validation, acknowledgement ownership and idempotent refunds.

Separate native-floor flag: `-bt-lab -bt-diagnostics -bt-vending-native-tour`. This starts a native run, creates a vending fixture with a native-layer collider, and invokes the actual host request and recipient receipt handlers against the native player's inventory. `artifacts/tests/vending-native-results.json` checks stock reservation, replayed request arbitration, quarter consumption, reward receipt and duplicate-grant rejection. The receipt uses the host-issued delivery token and the fixture's configured fixed reward. These checks do not constitute a physical UI click-through or a two-client socket purchase test.
